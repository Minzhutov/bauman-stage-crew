# Bauman Stage Crew — портал команды концертного продакшена

Многостраничный веб-портал для внутренней работы команды концертного
продакшена: публикация мероприятий с техническим заданием и набором
специалистов, учебные лекции («Академии»), база мануалов, рейтинг
участников по баллам и личный кабинет с должностями и ачивками.

## Стек

- Node.js + Express (сервер и роутинг)
- EJS — серверный рендеринг многостраничного сайта
- SQLite (`data/bsc.sqlite`, через `better-sqlite3`) — без отдельного
  сервера БД, один файл на диске, но настоящие ACID-транзакции
- express-session + connect-flash — сессии и всплывающие уведомления
- bcryptjs — хеширование паролей
- multer — загрузка файлов (мануалы, аватарки ачивок и профиля)
- nodemailer — отправка писем восстановления пароля (опционально, см. ниже)

## Запуск

```bash
npm install
npm start          # обычный запуск
# или
npm run dev         # запуск с автоперезапуском при изменении файлов
```

По умолчанию сайт поднимается на `http://localhost:3000` (переменная `PORT`).
Скопируйте `.env.example` в `.env`, чтобы задать свой `SESSION_SECRET` перед
использованием в проде.

При первом запуске (если `data/bsc.sqlite` отсутствует) база автоматически
наполняется демо-данными: каталог должностей, площадок, ачивок, несколько
мероприятий, лекций и учётные записи.

> До SQLite хранилищем был простой JSON-файл (`data/db.json`). При первом
> запуске на окружении, где ещё остался старый `data/db.json`, а
> `data/bsc.sqlite` ещё нет, `lib/store.js` один раз автоматически
> переносит все данные из JSON в SQLite — сама миграция ничего руками
> делать не просит, но файл `data/db.json` после этого можно удалить
> (он больше не читается) или оставить как исторический бэкап.

### Учётные данные по умолчанию

| Роль            | Email                              | Пароль        |
|-----------------|-------------------------------------|---------------|
| Администратор   | minzhutov@gmail.com                 | changeme123   |
| Участник команды| ivan.petrov@example.com и др.       | changeme123   |

**Смените пароль администратора после первого входа** (через раздел
«Профиль»). Первый когда-либо зарегистрированный через форму `/register`
пользователь автоматически становится администратором — это удобно для
первого разворачивания «с нуля» (без демо-данных), но означает, что делать
это должен доверенный человек.

## Структура разделов

- **Мероприятия** — администраторы публикуют события: время, место,
  техническое задание и список требуемых специалистов с количеством по
  каждой должности. Участники откликаются на подходящие им должности
  (только если такая должность указана в их профиле), администратор
  подтверждает заявки и по факту отработки мероприятия начисляет баллы.
- **Академии** — анонсы лекций: тема, направление, спикер, время и
  аудитория. С карточки лекции администратор начисляет баллы конкретным
  участникам по итогам посещения — как и на мероприятиях.
- **Мануалы** — загрузка и скачивание файлов документации (PDF, DOC(X),
  XLS(X), PPT(X), TXT, RTF, ZIP, изображения, до 25 МБ).
- **Таблица лидеров** — сводный рейтинг участников по баллам, с подиумом
  топ-3 и общей таблицей.
- **Профиль** — фото профиля (можно сменить или удалить, иначе — кружок
  с инициалом), контактные данные (email, телефон, учебная группа,
  «о себе»), баллы и их история (с указанием мероприятия/лекции, за
  которые начислено), список мероприятий, доступные должности и ачивки
  — отображаются как медали (аватарка или эмодзи-иконка + подпись).
  Баллы, ачивки и доступные должности назначает только администратор;
  баллы — по итогам мероприятий (закрытие смены) и академий (карточка
  лекции).
- **Админ-панель** (`/admin/...`) — добавление и удаление должностей,
  площадок и ачивок, управление пользователями (роли). Каталог
  должностей общий: используется и в требованиях мероприятий, и в
  профилях — список можно свободно расширять и сокращать, ссылки на
  удалённую должность корректно очищаются везде, где она использовалась.
  У ачивки можно задать уникальную аватарку (изображение) — если она не
  загружена, используется запасная эмодзи-иконка.

### Автоматические ачивки

Ачивке в каталоге можно назначить правило автоматического присвоения:
условие («метрика ≥ порог») и сам порог. Доступные метрики (см.
`lib/domain.js`, `AUTO_RULES`): число закрытых смен на мероприятиях,
сумма баллов, число лекций Академии с начисленными баллами, число
доступных должностей в профиле. Движок (`evaluateAutoAchievements`)
проверяет условие после каждого действия, способного повлиять на
метрику, — начисления баллов (в том числе за лекцию), закрытия смены
на мероприятии и изменения списка должностей — и выдаёт ачивку
автоматически, если условие выполнено и её ещё нет у пользователя. При
создании новой ачивки с правилом система сразу проверяет всех текущих
пользователей и задним числом выдаёт её тем, кто уже соответствует
условию. Ачивки без правила («только вручную») присваиваются и
отзываются администратором из профиля пользователя.

### Восстановление пароля по email

Ссылка «Забыли пароль?» на странице входа ведёт на `/forgot-password`:
пользователь указывает email, система создаёт одноразовый токен (срок
действия — 1 час) и отправляет письмо со ссылкой `/reset-password/<token>`
через `lib/mailer.js`. Ответ пользователю не показывает, найден ли email
в базе, — это защита от перебора адресов.

Отправка писем настраивается через переменные окружения (см.
`.env.example`): `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASS`,
`SMTP_FROM`. **Без этих настроек письмо не отправляется** — вместо этого
ссылка для сброса пароля выводится в консоль сервера (`[mailer] ...`),
что достаточно для локальной разработки и тестирования флоу без
реального почтового аккаунта.

## Роли и права доступа

- **Гость** — просмотр мероприятий, академий, мануалов, таблицы лидеров.
- **Участник команды** — плюс отклик на мероприятия по доступным ему
  должностям, просмотр и редактирование контактных данных в своём
  профиле.
- **Администратор** — плюс публикация/редактирование/удаление
  мероприятий и лекций, загрузка мануалов, подтверждение заявок и
  начисление баллов, назначение должностей и ачивок, управление
  каталогами должностей/площадок/ачивок и ролями пользователей.

## Деплой

**Нужен хостинг с постоянным диском** — обычный VPS (DigitalOcean, Timeweb,
Hetzner и т.п.) или PaaS с примонтированным persistent volume. Все данные
(мероприятия, пользователи, баллы — `data/bsc.sqlite`, а также загруженные
файлы — `public/uploads/`) лежат на диске самого процесса; serverless-
платформы и эфемерные контейнеры (Vercel, Netlify, большинство «пуш и
забыл» PaaS без volume) пересоздают файловую систему при каждом
передеплое — база и все загрузки при этом стираются.

### Перед первым запуском на сервере

1. Скопируйте `.env.example` в `.env` и задайте свой **`SESSION_SECRET`**
   (сгенерировать: `node -e "console.log(require('crypto').randomBytes(48).toString('hex'))"`)
   — не переиспользуйте секрет из локальной разработки. При желании
   реальных писем сброса пароля — заполните `SMTP_*` (иначе ссылка просто
   пишется в консоль, см. «Восстановление пароля по email» выше).
2. `npm install --omit=dev` (или обычный `npm install`). `better-sqlite3` —
   нативный модуль: для большинства платформ npm ставит готовый
   прекомпилированный бинарник сам, но в Docker/Alpine-окружениях иногда
   нужны build-инструменты в образе (`python3`, `make`, `g++`) — если
   `npm install` падает на этом пакете, добавьте их в Dockerfile.
3. Сайт должен быть доступен по HTTPS — обычно через обратный прокси
   (nginx/Caddy) на том же сервере, который сам получает сертификат
   (Let's Encrypt) и проксирует запросы на `PORT` из `.env`. Кука сессии
   использует режим `secure: 'auto'` — сама определяет HTTPS через
   `X-Forwarded-Proto` (`app.set('trust proxy', 1)` в `server.js`) и
   не потребует ручных правок при появлении прокси, но и не сломает вход,
   если прокси временно недоступен или ещё не настроен.
4. Запустите процесс через менеджер, который сам перезапустит сервер при
   падении или перезагрузке машины — вручную (`node server.js` /
   `nohup`) для постоянной работы не годится:
   - **pm2**: `npm install -g pm2`, затем `npm run pm2:start`, после —
     `pm2 save` и `pm2 startup` (пропишет автозапуск pm2 при старте ОС).
     Логи — `npm run pm2:logs`, перезапуск — `npm run pm2:restart`.
   - **systemd** (альтернатива): шаблон юнита в
     `deploy/bauman-stage-crew.service` — отредактируйте `User` и
     `WorkingDirectory` под свой сервер и следуйте комментариям в файле.

   `server.js` корректно обрабатывает `SIGTERM`/`SIGINT` (graceful
   shutdown) — дожидается завершения открытых запросов перед выходом,
   так что менеджеру процессов не приходится «убивать» его по таймауту.

### Резервное копирование

`data/bsc.sqlite` и `public/uploads/` — единственное, что не восстановить
из git при потере: код есть в репозитории, а вот мероприятия,
пользователи, баллы и загруженные файлы — только на диске сервера.
Бэкап снимается через нативный SQLite backup API (а не простым
копированием файла), поэтому безопасен даже при работающем сервере.

```bash
./scripts/backup.sh                 # бэкап в ./backups/ (по умолчанию)
BACKUP_DIR=/mnt/backups ./scripts/backup.sh
KEEP_DAYS=14 ./scripts/backup.sh     # хранить дольше 7 дней по умолчанию
```

Добавьте в `crontab -e` на сервере (ежедневно в 03:00):

```
0 3 * * * cd /var/www/bauman-stage-crew && ./scripts/backup.sh >> logs/backup.log 2>&1
```

**Важно:** приём «удалить `data/bsc.sqlite` и перезапустить сервер, чтобы
пересобрать демо-данные», которым мы пользовались при разработке, после
появления на сайте реальных пользователей и мероприятий применять
**нельзя** — это безвозвратно удалит всю боевую базу.

## Примечания

- Хранилище — SQLite (`better-sqlite3`, синхронный драйвер, режим
  `journal_mode = WAL`) с тем же простым интерфейсом (`find/where/insert/
  update/remove`), что был у прежнего JSON-файла — каждая коллекция
  хранится как отдельная таблица с JSON-блобом в колонке `data`, без
  отдельной типизированной схемы на каждое поле. Подходит для команды в
  десятки-сотни человек и одного процесса приложения; если понадобится
  несколько инстансов сервера с общей базой — это первое, что стоит
  заменить на клиент-серверную СУБД (Postgres/MySQL).
- Сессии хранятся в памяти процесса (`express-session` MemoryStore) —
  для продакшена с несколькими инстансами стоит подключить внешний
  session store.
